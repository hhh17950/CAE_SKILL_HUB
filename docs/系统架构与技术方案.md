# 系统架构与技术方案

## 范围与技术选择

服务封装脚本执行边界，不了解内部几何、网格、材料或求解器调用。一个业务流程对应一个提交接口；查询状态、结果和日志是公共任务管理能力，不代表新增 CAE 流程。

技术栈：FastAPI、Pydantic、asyncio、SQLAlchemy、标准库 sqlite3、SQLite、Alembic、Loguru、MCP Python SDK（`mcp` 2.x，`MCPServer` 直挂 Streamable HTTP）。面向 Linux 单机双容器、Python 3.10；不引入 Redis、队列框架或工作流引擎，也不再依赖 aiosqlite。

```text
Agent ─HTTP→ API 容器 ─线程池/SQLAlchemy→ SQLite ←线程池/SQLAlchemy─ Worker 容器
              │                                   │
              └─查询状态/受保护的日志               └─asyncio subprocess
                                                      └─固定流程脚本
```

API 返回 HTTP 202。Worker 独立运行，串行领取任务，不占用 HTTP 请求生命周期。等待子进程采用异步 I/O；脚本自身的长耗时步骤不阻塞服务。stdout/stderr 直接写文件，避免管道积压和全量内存缓存。

## 分层职责

| 位置 | 职责 |

| `api/schemas.py` | 响应模型与 RFC 9457 错误结构；请求参数在路由中用 Form/File 声明 |

| `api/routes/docs.py` | Swagger 页面，本地资源、不依赖 CDN，不进入业务 OpenAPI |
| `api/router.py` | 注册路由；异常、OpenAPI、请求体限制等文件保留在 api 外层 |
| `services/modal.py` | 固定命令、参数与环境变量映射 |
| `services/paths.py` | 任务目录与日志、结果路径的唯一来源 |
| `services/executor.py` | 子进程、超时、进程组清理，不理解具体 CAE 语义 |

## 状态与恢复

状态：`queued → running → succeeded / failed / timed_out / unknown`。

- `succeeded`：退出码为 0，不保证物理结果正确或云图文件存在。
- `failed`：非 0 退出或启动/执行器错误；无退出码时为 null。
- `timed_out`：超时后终止进程组，记录退出码。
- `unknown`：Worker 被中断，或启动时发现遗留 running 任务，需人工核对。

每次提交生成新 `run_id`，不自动重试。领取使用 SQLite `BEGIN IMMEDIATE` 事务。Worker 用 `flock` 保证同一数据库仅一个正式 Worker；文件可保留，内核锁随进程退出释放。生产不得直接调用测试用途的 `run_once()` 绕过锁。

SIGTERM/SIGINT 会触发清理；SIGKILL、断电不能保证数据库状态及时更新。进程组清理无法覆盖主动脱离进程组的 GUI。真实启动器必须前台等待流程结束；若启动 GUI 后立即返回 0，不能据此认定整个 CAE 流程完成。Compose 使用 init 和 45 秒停止宽限；重启 API 不停止 Worker，重建 Worker 或整套 down 则会中断执行。

## 数据库与迁移

SQLite 保存参数快照、状态、时间、退出码和简要错误，工程/日志/结果保存在文件系统。`guie_runs.owner` 是历史遗留字段，当前固定写入 `public`，不参与隔离。运行时统一由 SQLAlchemy 管理：同步 Session 在 asyncio 线程池中创建、执行、提交/回滚、关闭，不跨线程共享 Session 或连接。每个操作返回普通字典而非仍依赖 Session 的对象；NullPool 避免长时间保留空闲连接。脚本执行期间不持有事务。

SQLite 日志模式统一为 `DELETE`（传统回滚日志），不再主动启用 WAL，以适配当前 Navicat 的打开行为。DELETE 不是删除数据库数据，而是提交后清理回滚日志；它的读写并发能力与 WAL 不同，因此继续采用单 Worker、短事务和 30 秒锁等待。该调整不改变表结构，也不新增表迁移版本。

这不是原生异步数据库驱动，而是同步数据库访问的线程池隔离。取消 await 不能终止底层线程，因此桥接层会等待正在执行的事务结束，再传播取消，避免 Worker 锁已释放但旧领取事务仍在提交。正常停止期间可能等待 SQLite 的锁超时（30 秒）。

Alembic 同样使用 SQLAlchemy，是人工执行的管理命令，不在 API 或 Worker 启动过程中执行。此次只更换数据库访问方式，表结构和现有迁移版本不变，不生成空迁移、不重建已有库。

迁移目录来自 `alembic init` 标准脚手架，含 `env.py`、`script.py.mako`、`versions/`；初始版本通过 `revision --autogenerate` 生成。服务启动只检查版本，缺库或版本不符则报错。当前使用新数据库基线，不自动兼容历史表结构。

## 边界与安全

- 服务自身不做鉴权，也不按调用方隔离任务：任何能访问服务地址的调用方都能读取任意 `run_id` 的状态、结果和日志。访问控制由部署层（反向代理或网络策略）承担。
- 几何模型由调用方上传，服务按字节写入 `<CAE_WORKSPACE_ROOT>/<run_id>/model/`，既不解析内容，也不接受调用方给出的服务端路径；上传大小受 `CAE_MAX_MODEL_BYTES` 限制。这不是恶意本地用户的沙箱，共享目录权限仍须运维管理。
- 工程目录、日志和结果路径全部由 `services/paths.py` 在 `CAE_WORKSPACE_ROOT` 下按 `run_id` 生成，调用方不能指定。任务目录在提交时以 `mkdir(exist_ok=False)` 独占创建，不会覆盖已有任务的结果。
- 调用方不能指定命令、脚本或任意环境变量；不使用 shell。输出路径由服务生成。
- 只把 `static/docs` 作为静态目录挂载，不公开整个 `static`；日志通过接口读取。
- 默认请求体限制 100 MiB（`CAE_MAX_REQUEST_BYTES`），上传几何模型限制 50 MiB（`CAE_MAX_MODEL_BYTES`）。任务日志无大小配额、无自动清理，需要磁盘监控和保留策略。
- 单 API 进程、单 Worker、本地磁盘 SQLite；不支持多机或网络盘 SQLite。
- `/healthz` 仅表示 API 存活，不表示 Worker、GUI 或求解器健康。

MCP 已实现：同一个 FastAPI 应用在 `/mcp` 上挂载 MCP（Streamable HTTP）子应用，提供 `submit_modal_run`、`get_run_status`、`get_run_result`、`get_run_log` 四个工具，复用同一任务表、任务目录和 Worker，不另建执行器。`services/mcp_server.py` 负责工具定义，`main.py` 在 lifespan 中启动 MCP 的 session manager（`app.mount()` 不会运行子应用 lifespan）。传输层的 Host 校验按内网自用场景关闭（服务自身无鉴权，访问控制由部署层负责），避免内网地址访问被拒；`CAE_PUBLIC_BASE_URL` 只用于生成云图下载 URL。用配置项 `CAE_MCP_ENABLED` 可以关闭该端点。

## 容器边界

API 和 Worker 使用同一镜像、不同命令，Worker 不暴露端口，也不依赖 API 先启动。共享 `${WORKSPACE}:/opt/cae_service/workspace`（任务目录、数据库、服务日志都在其中），CAE 安装目录以 `${SSTA_CAE_PATH}:/opt/ssta-cae` 只读方式挂给双方。数据库使用 DELETE 模式，仍需挂载整个父目录以创建回滚日志，不单独挂载 db 文件。

`docker-compose.yaml` 直接定义 API 和 Worker，不使用公共 YAML 模板。Dockerfile 指定 UID/GID 10001，Compose 保留模型只读挂载、init、重启策略和停止宽限；不使用 privileged、宿主机 PID 空间或 Docker socket。简化配置未启用只读根文件系统和额外安全选项，生产部署可按实际要求增加。输入目录必须事先存在。此配置运行测试脚本；真实 GUI 的容器依赖必须在接入时验证，容器内启动二进制不等于操作宿主机桌面。

Swagger 的离线资源固定在 `static/docs`，镜像构建直接复制已入库文件，不在运行时访问外网。只公开该子目录，绝不公开 static/logs；`/redoc` 停用。文档页面和业务接口都不做鉴权，部署方应通过反向代理或网络策略限制访问。
